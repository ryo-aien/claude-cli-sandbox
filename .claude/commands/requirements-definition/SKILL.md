# 要件定義スキル

Web アプリ開発の要件を対話で整理し、要件定義書を Markdown で出力する。

## ワークフロー

```
1. ヒアリング（対話で要件を引き出す）
2. 要件整理（収集した情報を構造化）
3. 要件定義書生成（Markdown ファイルを出力）
```

## Phase 1: ヒアリング

以下のカテゴリを順番に確認する。一度に多くの質問をせず、2〜3問ずつ聞く。

### 1.1 プロジェクトの全体像

最初に聞くこと:
- 何を作りたいか（一言で）
- 誰が使うか
- なぜ作るか（解決したい課題）

### 1.2 機能要件

全体像を把握した後:
- 必須の機能は何か
- ユーザーがシステムで行う主な操作は何か
- 入出力データは何か

### 1.3 非機能要件

機能が見えてきた後:
- 想定ユーザー数・同時接続数
- セキュリティ要件（認証・認可）
- 技術スタックの希望や制約

### 1.4 スコープ確認

最後に:
- 初期リリースに含めるもの・含めないもの
- 既知の制約（予算・期間・技術）

### ヒアリングのルール

- ユーザーの回答が曖昧な場合は具体例を提示して確認する
- 「特にない」「おまかせ」と言われた場合はベストプラクティスを提案する
- 各カテゴリの完了後に、理解した内容を箇条書きで要約して認識合わせする
- 全カテゴリのヒアリングが完了したら Phase 2 に進む

## Phase 2: 要件整理

ヒアリング結果を以下の観点で整理する:

- 機能に ID を振る（FR-001, FR-002...）
- 優先度を分類する（Must / Should / Could）
- 不明点・未確定項目を「TBD」として明記する
- 矛盾する要件があれば指摘してユーザーに確認する

整理結果をユーザーに提示し、過不足がないか確認を取る。

## Phase 3: 要件定義書生成

ユーザーの承認後、[references/template.md](references/template.md) のフォーマットに従って要件定義書を生成する。

出力ルール:
- ファイル名: `REQUIREMENTS.md`（プロジェクトルートに配置）
- 不明な項目は「TBD」とし確認が必要な旨を注記する
- ヒアリングで出なかった非機能要件は Web アプリのベストプラクティスで埋める
- 生成後、ユーザーにレビューを依頼し、フィードバックに基づいて修正する
