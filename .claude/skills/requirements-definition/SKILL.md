# 要件定義スキル

ユーザーの要件定義作業を支援する。成果物は原則Markdownの要件定義書。

## 全体の流れ

1. モードを判定する（明らかな場合は聞かずに進む）
2. プロジェクト種別と前提を確認する
3. モードに応じた作業を行う
4. Markdownの要件定義書ファイルを作成して渡す

## ステップ1: モード判定

ユーザーの依頼から次の4モードのどれかを判定する。

- **ヒアリングモード**: 「一緒に考えたい」「まだ頭の中にしかない」など、材料が乏しい場合
- **生成モード**: 議事録・メモ・企画書・チャットログなどの材料が提供されている場合
- **レビューモード**: 既存の要件定義書が提供され、レビューや改善を求められている場合
- **技術仕様モード**: 要件が固まった後、「どんな技術で作るか」を決める段階。「技術仕様書」「技術選定」「何で作ればいい？」などの依頼、または要件定義書完成後の次工程として

材料が添付されていれば生成かレビュー、何もなければヒアリング、と判断できることが多い。曖昧なときだけ確認する。要件定義書が完成したら、次工程として技術仕様書の作成を提案する。

## ステップ2: プロジェクト種別と前提の確認

作業を始める前に、以下を選択式で確認する（すでに会話から明らかな項目は聞かない）。ask_user_input_v0 のような選択式入力ツールが使える環境ではそれを使う。

**質問の順番が重要。** 前の回答が次の質問の選択肢を決めるため、必ずこの順で聞く。一度に全部聞かず、①②を先に聞いてから、その回答を踏まえて③④の選択肢を組み立てる。

① **プロジェクト種別**: 業務システム開発 / 社内ツール・DX / Webサービス・アプリ / パッケージ導入・SaaS選定 / その他

② **システム規模**: ユーザーが判断できるよう、目安を添えて提示する。

- **小規模**: 利用者〜10名程度、単一部署、主要機能が数個（例: 一部署の申請管理ツール）
- **中規模**: 利用者〜100名程度、複数部署にまたがる、外部連携が1〜2本（例: 全社の経費精算システム）
- **大規模**: 全社・社外利用、基幹業務、複数システム連携、段階リリース前提（例: 販売管理の刷新）

③ **読み手**: 開発ベンダー（発注用） / 社内開発チーム / 経営層・意思決定者 / 自分用の整理

④ **フェーズ**: 構想段階 / 予算取り・稟議前 / 開発着手前の詳細化

**選択肢は文脈から生成する。** ③④の選択肢は上記の汎用リストをそのまま出すのではなく、①②の回答と会話内容に合わせて具体化する。例えば「社内ツール・小規模」なら③の選択肢から「開発ベンダー」を外して「情シスに依頼」「自分でノーコードで作る」を加える、「Webサービス・大規模」なら④に「投資家向け資料の前段階」を加える、といった調整をする。ユーザーが自分の状況を選択肢の中に見つけられることが目的。

回答の使い方: 規模は文書の粒度を決める（小規模ならテンプレートを大胆に削り、大規模なら移行・段階リリース・体制の章を厚くする）。読み手は書き方を決める（ベンダー向けなら曖昧さを排し見積もり可能な粒度に、経営層向けなら背景・効果を厚く、自分用なら論点の可視化を優先）。

## ステップ3: モード別の作業

### ヒアリングモード

`references/hearing-guide.md` を読み、そこにある質問バンクを使ってヒアリングする。

重要な進め方の原則:

- 一度に大量の質問を投げない。1ターンに1〜3問、選択肢付きで聞く。
- 「背景・目的 → 現状と課題 → スコープ → 業務・機能要件 → 非機能・制約」の順に大枠から詳細へ進む。この順序は、前の回答が次の質問の選択肢の材料になるという理由でも重要。
- 選択肢はそれまでの回答から具体的に組み立てる。例えば「現状はExcelで管理」と聞いた後の移行の質問なら、選択肢は「既存Excelのデータを取り込みたい / 新規スタートでよい / 一部だけ移行」のようにユーザーの状況の言葉で出す。汎用的な選択肢の使い回しは、ユーザーに翻訳の負担を強いるので避ける。
- ユーザーの回答から推測できることは質問せず、仮置きして「〜と仮定しました。違ったら教えてください」と明示する。ユーザーの負担を最小にすることが最優先。
- 2〜3往復ごとに、それまでの内容を要件定義書の骨子として見せる。完成を待たせるより、育っていくドキュメントを見せた方が認識齟齬が早く見つかる。
- すべて聞き切る必要はない。ユーザーが「もういい」「一旦まとめて」という空気を出したら、未確定項目を「TBD（要検討）」として明示した上でまとめに入る。

### 生成モード

1. 提供された材料をすべて読む。
2. `references/template.md` の構成に材料の内容をマッピングする。
3. 材料に書かれていないことを勝手に創作しない。これが生成モードで最も重要な原則。埋まらない項目は削除せず「TBD: ◯◯について要確認」と残す。TBDは論点リストとしての価値がある。
4. 材料内の矛盾（例: 議事録Aと議事録Bで納期が違う）を見つけたら、どちらかに寄せずに矛盾として明記し、ユーザーに確認する。
5. 生成後、「材料から読み取れなかった重要事項」を3〜5個リストアップしてユーザーに提示する。

### レビューモード

1. `references/review-checklist.md` を読み、チェックリストに沿って既存文書を評価する。
2. 指摘は「重大（このままだと手戻り・失注・訴訟リスク）/ 中（曖昧で解釈が割れる）/ 軽微（体裁・表現）」の3段階で分類する。
3. 各指摘には必ず「なぜ問題か」と「修正案」をセットで付ける。ダメ出しだけのレビューはしない。
4. ユーザーが望めば、指摘を反映した改訂版Markdownを作成する。

### 技術仕様モード

`references/tech-spec-guide.md` を読み、質問バンクに沿って進める。要件定義と同じく選択式・段階的に聞くが、追加で守るべき原則:

1. **要件定義書があればまず読む。** 会話内やファイルに要件定義書があれば、規模・利用者・連携・非機能要件から答えを先に拾い、判明していることは聞き直さない。要件定義書がない場合は、最低限の前提（ステップ2の①②相当＋利用者数・アクセス方法）だけ先に確認する。
2. **質問は「体制 → 制約 → 方式 → デプロイ先 → 個別技術 → ローカル開発環境」の順。** 最初に「誰が作るか」を聞く（ノーコードやベンダー発注なら以降の大半が不要になるため）。デプロイ先は制約・契約から決まり技術の選択肢を絞るので個別技術より先、ローカル環境は「本番をどう手元で再現するか」なのでデプロイ先確定後に聞く。
3. **全質問に「わからない / 推奨に任せる」を入れる。** ユーザーは技術に詳しくない前提。任された項目はClaudeが要件に基づいて決め、理由と代替案を仕様書に明記する。
4. 成果物は `references/tech-spec-template.md` の構成で作成する。ファイル名は `技術仕様書_<プロジェクト名>_<YYYYMMDD>.md`。要件IDと技術選定の対応を必ず取る。

## ステップ4: 成果物の作成とダウンロード提供

- 要件定義書は `references/template.md`、技術仕様書は `references/tech-spec-template.md` の構成をベースにMarkdownファイルを作成する。プロジェクトに合わない章は削る（例: 画面を持たないバッチシステムに画面一覧は不要）。テンプレートは網羅リストであって強制ではない。
- ファイル名は `要件定義書_<プロジェクト名>_<YYYYMMDD>.md` / `技術仕様書_<プロジェクト名>_<YYYYMMDD>.md` とする。
- 未確定事項はすべて `**TBD:**` プレフィックスで統一し、文書末尾に「未確定事項一覧」として集約もする。検索性と、次のアクションの明確さのため。
- **成果物は必ずダウンロード可能なファイルとして渡す。** チャット本文に全文を貼るだけで終わらせない。ファイルを出力ディレクトリ（Claude.aiなら `/mnt/user-data/outputs/`）に保存し、present_files 等のファイル提示ツールでユーザーに渡す。
- **要件定義書と技術仕様書の両方を作った場合は、最後に2ファイルまとめて提示する。** 技術仕様書の完成時点で、対応する要件定義書（改訂していれば最新版）も一緒に present_files に渡し、セットでダウンロードできるようにする。2つの文書はバージョン対応が命なので、片方だけ手元に残る状態を作らない。
- 文書を改訂したら、ファイル内のバージョン番号を上げて再提示する。

## 品質の原則（全モード共通）

- **曖昧語を避ける**: 「柔軟に」「適切に」「高速に」「使いやすく」は要件として機能しない。数値・条件・具体例に落とすか、落とせないならTBDにする。
- **要求と要件を区別する**: ユーザーの「〜したい」（要求）をそのまま書かず、「システムは〜できること」（要件）に変換する。
- **スコープ外を明記する**: やらないことを書くのは、やることを書くのと同じくらい重要。後の「言った言わない」を防ぐ。
- **機能要件にはIDを振る**: `FR-001` 形式。非機能要件は `NFR-001`。後工程でのトレーサビリティのため。
- **1要件1文**: 「AかつBができ、さらにCの場合はD」のような複合要件は分割する。
