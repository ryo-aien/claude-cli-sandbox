## 1. 本書の位置づけ

> 要件定義書のどの要件を、どの技術で実現するかを定める文書であること。読み手（ベンダー/社内チーム）と、指定事項・推奨事項・提案に委ねる事項の区別を冒頭で宣言する。

## 2. システム全体構成

> 構成図（Mermaid可）と、主要コンポーネントの一覧。利用者→フロント→バックエンド→DB→外部連携の流れがひと目でわかること。

## 3. 方式設計

| 項目 | 採用方式 | 理由 |
|---|---|---|
| 提供形態 | 例: Webアプリ（レスポンシブ） | スマホ利用要件(NFR-xxx)のため |
| 認証方式 | 例: Microsoft Entra ID (SSO) | 社内標準がM365のため |
| データ配置 | 例: 国内リージョンのクラウド | 社内規程による |

## 5. 環境構成

> ローカル開発環境から本番までの一覧。「どこで・何が動くか」がひと目でわかること。

| 環境 | 場所（デプロイ先/マシン） | 用途 | 備考 |
|---|---|---|---|
| ローカル開発 | 例: 各開発者のPC（Win/Mac混在、Docker利用） | 開発・単体確認 | セットアップ手順はREADMEに |
| ステージング | 例: ◯◯クラウド（本番と同構成・縮小版） | 受け入れ確認 | 小規模なら省略可 |
| 本番 | 例: ◯◯クラウド 国内リージョン | 実運用 | データ配置制限: あり/なし |

> ローカル開発環境の欄には、OS・ランタイムのバージョン・コンテナ利用の有無・本番との差異（あれば）を明記する。「手元では動いたのに本番で動かない」の主因は環境差異なので、差異は意図的に許容したものだけに限定し、それを文書に残す。
