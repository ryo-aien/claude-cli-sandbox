# 要件定義書レビューチェックリスト

レビューモードで使う。各項目を評価し、指摘は 重大 / 中 / 軽微 に分類。必ず「なぜ問題か」+「修正案」をセットで示す。

## A. 目的・スコープ（ここの欠陥は重大になりやすい）

- [ ] 背景・目的が書かれており、機能の羅列だけになっていないか
- [ ] スコープ外（やらないこと）が明記されているか
- [ ] 前提条件・制約（予算、納期、法規制、既存システム）が書かれているか
- [ ] 期待効果に定量的な根拠があるか（なくても致命的ではないが、稟議用途なら重大）

## B. 機能要件

- [ ] 各要件にIDが振られているか
- [ ] 1要件1文になっているか（複合要件は分割を提案）
- [ ] 「〜したい」（要求）のまま書かれておらず、「〜できること」（要件）になっているか
- [ ] 曖昧語（柔軟に・適切に・使いやすく・高速に・など）が要件文に残っていないか
- [ ] 優先度が付いているか。全部Must/高になっていないか（優先度の意味がない）
- [ ] 例外系・エラー時の扱いに言及があるか（正常系だけの要件定義書は非常に多い）

## C. 非機能要件

- [ ] そもそも非機能要件の章があるか（ないケースが最多の重大指摘）
- [ ] 性能・可用性・セキュリティ・運用の4つは最低限カバーされているか
- [ ] 「特になし」なのか「検討漏れ」なのか区別できるか
- [ ] 数値のない非機能要件（「高速であること」等）が放置されていないか

## D. データ・連携

- [ ] 既存データの移行有無・件数規模に言及があるか
- [ ] 外部システム連携の有無と方式が書かれているか

## E. 整合性・読みやすさ

- [ ] 文書内で矛盾がないか（章をまたいだ数値・納期・スコープの食い違い）
- [ ] 社内用語・略語が定義されているか（読み手が社外の場合は重大）
- [ ] 未確定事項がTBDとして可視化されているか。曖昧なまま断定調で書かれていないか

## F. 読み手適合性

- [ ] ベンダー発注用: 見積もり可能な粒度か？（規模感・件数・画面数がないと見積不能）
- [ ] 経営層向け: 効果とコストが最初の2ページで伝わるか？
- [ ] 開発チーム向け: 受け入れ条件が判断可能か？

## レビュー結果の出力形式

```markdown
# レビュー結果: <文書名>

## 総評
（2〜3文。良い点も必ず1つは挙げる）

## 指摘事項

### 重大
| # | 箇所 | 指摘 | なぜ問題か | 修正案 |
|---|---|---|---|---|

### 中
（同形式）

### 軽微
（同形式）

## 推奨する次のアクション
（優先順位付きで3つ以内）
```
