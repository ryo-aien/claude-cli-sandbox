# 技術仕様ヒアリングガイド

技術仕様モードで使う質問バンク。要件定義以上に「ユーザーは技術に詳しくない」前提で進める。

## 大原則

- **要件定義書から答えを先に拾う。** 規模・利用者数・社内/社外・連携・セキュリティ要件・モバイル利用の有無は要件定義で判明済みのはず。判明していることは絶対に聞き直さない。
- **すべての質問に「わからない / 推奨に任せる」の選択肢を必ず入れる。** これを選ばれたらClaudeが要件から推奨を決め、理由付きで仕様書に書く。ユーザーに技術判断を強制しない。
- **技術名で聞かず、状況で聞く。**「Reactにしますか？」ではなく「社内で今使っている技術はありますか？」。選択のあと、Claudeが技術に翻訳する。
- **質問の順番: 体制 → 制約 → 方式 → デプロイ先 → 個別技術 → ローカル開発環境。** 前の回答が後の選択肢を大きく絞る。「ノーコードで作る」なら以降の言語・環境の質問はすべて不要。デプロイ先を個別技術より先に聞くのは、契約済みクラウドや社内規程がデプロイ先を決め、デプロイ先が技術の選択肢を絞るから（例: Azure契約済みならMicrosoft系スタックが有力になる）。ローカル環境を最後に聞くのは、「本番環境を手元でどう再現するか」という問いであり、デプロイ先が決まらないと答えが出ないから。

## フェーズ1: 誰が作るか（最初に必ず。ここで以降の質問の7割が決まる）

- 開発するのは？
  - 社内のエンジニア / 開発ベンダーに発注 / 自分・非エンジニアがノーコード・ローコードで / AIツールを使って自分で / 未定・相談したい

> 「ベンダー発注」なら技術仕様書は指定事項と推奨事項を分ける（縛りすぎると提案の余地と価格競争力を奪う）。「ノーコード」なら技術スタックの章はツール選定の章に置き換える。

## フェーズ2: 社内の制約・既存資産

- 社内で標準として使っている技術・契約済みのサービスはありますか？
  - （文脈から候補を生成。例: Microsoft 365を使っていると判明していれば「Microsoft系で揃えたい（Power Platform / Azure）」を選択肢に入れる）
  - 特にない・わからない
- 会社のルールで、データの置き場所に制限はありますか？
  - クラウドOK / 国内サーバー限定 / 社内サーバーのみ（オンプレ） / わからない→情シスに確認（TBD）

## フェーズ3: 方式の大枠

- 利用者はどうやってアクセスしますか？（要件定義から推測して確認形式で）
  - 例: 「社内100名がPCとスマホから、と伺ったので、ブラウザで使えるWebアプリを想定しますが良いですか？」→ はい / アプリストアのアプリが必要 / PCインストール型がいい
- 認証（ログイン）は？（文脈から生成）
  - 例: 社内ツールなら「会社のGoogle/Microsoftアカウントでログイン / 独自のID・パスワード / ログイン不要」

## フェーズ4: デプロイ先（どこで動かすか）

> フェーズ2の回答（契約済みサービス、データ配置制限）から選択肢を生成する。制限に反する選択肢は最初から出さない。

- システムをどこで動かしますか？
  - すでに契約しているクラウドがある（AWS / Azure / GCP / さくら等 → フェーズ2の回答から具体名で提示）
  - 社内のサーバーで動かす（オンプレ）
  - 新しく借りる → 推奨してほしい
  - わからない / 推奨に任せる

> 「推奨に任せる」の場合の目安: 小規模・低予算ならPaaS・マネージド系（サーバー管理不要のもの）を第一候補に。運用者が非エンジニアならなおさら。オンプレは明確な規程・理由がある場合のみ。

- （新規に借りる場合）本番のほかに、試し用の環境（ステージング）は必要ですか？
  - 本番だけでよい（小規模向け） / 本番＋テスト環境 / わからない→規模から推奨

## フェーズ5: 個別技術（体制が「社内エンジニア」か「自分でAI開発」の場合のみ）

- 使い慣れた言語・フレームワークはありますか？（自由回答＋「特にない→推奨して」）
  - デプロイ先が決まっていれば、それと相性の良い候補を添えて提示する
- データベースのこだわりは？（あれば / 推奨に任せる）

> ベンダー発注の場合、この章は質問せず「ベンダー提案に委ねる事項」として仕様書に列挙する。

## フェーズ6: ローカル開発環境（フェーズ5と同じ条件のときのみ）

> ここの目的は「本番と同じ挙動を手元で再現できるか」と「開発者が今日から作業を始められるか」の2点。

- 開発に使うPCは？
  - Windows / Mac / Linux / 複数人で混在 / わからない
- 手元に本番とそっくりな環境を作りたいですか？（コンテナ＝Dockerの利用を、この言い方で聞く）
  - 本番と同じ環境を手元で再現したい（環境差異のトラブルを防げる。ただし初期セットアップの学習が要る）
  - 手元は簡易でよい（すぐ始められる。小規模・一人開発ならこれで十分なことが多い）
  - わからない / 推奨に任せる

> 推奨の目安: 複数人開発・OS混在・本番がコンテナ基盤ならDockerを推奨。一人開発・小規模・ノーコード寄りなら言語標準のツールだけで簡易に。ここでも過剰装備を避ける。

- ローカルのデータベースやテストデータはどうしますか？
  - 本番と同種のDBをローカルに立てる / 軽量なもので代用（SQLite等） / 共有の開発用DBに繋ぐ / 推奨に任せる

## フェーズ7: 運用・予算

- 月額でかけられるインフラ・ツール費用の目安は？
  - なるべく無料に近く / 〜1万円 / 〜10万円 / 要件次第で柔軟に / わからない
- 完成後の面倒を見るのは誰ですか？
  - 作った本人 / 情シス / ベンダーに保守委託 / 未定（TBD）

## 推奨を決めるときの考え方

「推奨に任せる」を選ばれた場合、以下を優先順に考慮して決め、**必ず理由と代替案を仕様書に書く**:

1. 運用する人が維持できるか（作れる技術より、保守できる技術）
2. 社内の既存資産との親和性
3. 規模に対する過剰・過少がないか（10名の社内ツールにKubernetesは要らない。逆に全社基幹にスプレッドシート直結は危うい）
4. 実績と情報量が十分に多い枯れた選択肢か

流行や新しさを理由に選ばない。仕様書の読み手が数年後にメンテナンスすることを想像して選ぶ。
