# 既存コードに合わせた修正の手順

このスキルの目的はただ一つ:
**修正後のコードが、最初からそのプロジェクトにあったかのように見えること。**

自分の知っているベストプラクティスより、そのプロジェクトの既存パターンを優先する。

---

## フェーズ1: 修正前の調査(必須)

コードを書き始める前に、必ず以下を調査する。

### 1-1. 修正対象の周辺を読む

- 修正対象のファイル全体を読む(該当行だけ見て書き始めない)
- 同じディレクトリの兄弟ファイルを1〜2個読む

### 1-2. 「お手本」を探す

これから書く処理と似たことをしている既存コードを検索して見つける。

- 同種の処理(例: 別のAPIエンドポイント、別のバリデーション、別のボタン)を grep で探す
- 見つけたら、それを今回の修正の「お手本」として構造・命名・書き方を踏襲する
- お手本が複数あり書き方が割れている場合は、**より新しい方**(git log で確認)か、
  **修正対象ファイルに近い方**に合わせる

### 1-3. プロジェクトの暗黙のルールを把握する

修正対象ファイルとお手本から、以下を読み取ってメモする:

| 観点 | 確認すること |
|---|---|
| 命名 | 変数・関数・ファイル名のケース、接頭辞/接尾辞のパターン |
| インポート | 相対パスかエイリアスか、並び順、default/named の使い分け |
| エラー処理 | try-catch の粒度、独自例外の有無、エラーの握り方/投げ方 |
| 非同期 | async/await か Promise チェーンか、並行処理の書き方 |
| ログ | 使っているロガー、console.log の許容度 |
| コメント | 量・言語(日本語/英語)・JSDoc等の形式 |
| テスト | 対応するテストファイルの場所と書き方 |
| 型 | 型注釈の厳格さ、any の許容度、型の定義場所 |

### 1-4. 設定ファイルを確認する

リポジトリルートにあれば読む: リンター/フォーマッタ設定(.eslintrc, .prettierrc,
ruff.toml, .editorconfig 等)、CLAUDE.md、CONTRIBUTING.md、既存の .claude/skills/。
明文化されたルールがあればそれが最優先。

## フェーズ2: 修正の原則

### 差分は最小にする

- 依頼された変更に必要な行だけを触る
- **やらないこと**: 無関係な箇所の整形・リネーム・リファクタリング、
  インポートの並べ替え、コメントスタイルの統一、空白の変更
- 「ついでに直したい」箇所を見つけたら、勝手に直さず修正完了後に提案として報告する

### 既存パターンを踏襲する(たとえ古くても)

- プロジェクトが古い書き方で統一されているなら、修正もその書き方で行う
  (例: 周囲が Promise チェーンなら async/await に書き換えない)
- 既存パターンに明確な問題(バグ・脆弱性)がある場合のみ、その旨を指摘した上で
  ユーザーに判断を仰ぐ。無断で「改善」しない

### ライブラリの追加は、確認の上で自律的に判断してよい

- まず既存の依存で実現できないか探す(車輪の再発明も、不要な追加も避ける)
- 既存で実現できず新しいライブラリが必要な場合は、以下を確認した上で
  問題がなければ**追加してよい**:
  - [ ] メンテナンスされているか(最終リリース時期、既知の重大な脆弱性の有無)
  - [ ] ライセンスがプロジェクトで利用可能か(MIT/Apache-2.0等。GPL系は要注意)
  - [ ] 十分に普及・実績があるか(ダウンロード数、利用実績)
  - [ ] プロジェクトの既存依存と競合・重複しないか
- 追加するときはプロジェクトの流儀に従う(パッケージマネージャの種類、
  バージョン固定の方針、lockファイルの更新を既存に合わせる)
- 完了報告で「何を・なぜ追加したか」と上記の確認結果を必ず報告する
- 上記の確認で懸念が残る場合(ライセンスが不明瞭、メンテが止まっている等)は
  追加せず、ユーザーに判断を仰ぐ
- 既存ライブラリのバージョン変更は、依頼された修正に必須の場合を除き行わない

### 既存の共通機能を再利用する

- ユーティリティ関数・共通コンポーネント・定数が既にないか、書く前に grep で探す
- 既存と重複する実装を新しく作らない

### インターフェースを壊さない

- 既存関数のシグネチャ・APIのレスポンス形式・DBスキーマを変える場合は、
  呼び出し元・利用箇所をすべて grep で洗い出し、影響範囲を報告してから変更する

## フェーズ3: 修正後のセルフチェック

完了報告の前に必ず確認する:

- [ ] diff を見て、依頼と無関係な変更が混ざっていないか
- [ ] 新しく書いた部分だけ浮いて見えないか(命名・構造がお手本と一致しているか)
- [ ] プロジェクト既存のテスト・リンター・型チェックのコマンドを探して実行したか
      (package.json の scripts、Makefile、CI設定ファイルから見つける)
- [ ] 修正対象に対応する既存テストがあれば、同じスタイルでテストを追加/更新したか

## 完了報告に含めること

1. 変更したファイルと変更内容の要約
2. お手本にした既存コード(あれば)
3. 実行した確認コマンドと結果
4. 追加したライブラリとその理由・確認結果(あれば)
5. 「ついで修正」候補として気づいたが触らなかった点(あれば)
